Create an agent team with following agent candidates to solve this problem:

Shared contract: every subagent returns JSON with exactly {question_id, verdict, sql, refusal, issues[], evidence[]}. verdict is one of pass|needs_revision|refuse. sql is non-empty only when verdict=pass. refusal is true only when verdict=refuse. issues[] lists concrete, question-specific defects with suggested fixes. evidence[] cites schema columns, question clauses, or executed result snippets. The orchestrator is the only writer of queries.json and must not accept a subagent verdict without checking its evidence.

1. Orchestrator (coordinator). Reads schema and questions, classifies each request as allowed SELECT or prohibited write/external-file/extension/database access. For allowed questions, it drafts SQL and dispatches parallel specialist reviews. It owns the final queries.json and must preserve requested column order, row ordering, ties, grouping, NULL behavior, and generalization. It may recall any specialist with a narrower scope and updated acceptance criteria. It resolves conflicts by requiring evidence, not authority.

2. SQL Semantics Reviewer. For each allowed question, independently checks the draft SQL against the question's requested columns, filters, grouping, NULL handling, ordering, and tie-breaking. Output to orchestrator: {question_id, verdict, sql, refusal, issues[], evidence[]}. If verdict=needs_revision, issues[] must name the exact clause or expression to change and evidence[] must quote the relevant question phrase or schema column.

3. Refusal Boundary Auditor. For every question, independently decides whether it is a prohibited write, external file, extra database, or extension request. Output to orchestrator: {question_id, verdict, sql, refusal, issues[], evidence[]}. If verdict=refuse, refusal=true and evidence[] must cite the prohibited phrase. If verdict=pass, refusal=false and evidence[] must show why the request is a read-only SELECT over the supplied repositories schema.

4. Execution Probe Agent. Runs candidate SQL against the supplied SQLite database with uv run and reports row counts, column names, NULL counts, and tie behavior. Output to orchestrator: {question_id, verdict, sql, refusal, issues[], evidence[]}. evidence[] must include observed column order and row order for the candidate query. It never edits queries.json.

Orchestrator loop: (a) draft all allowed SQL and refusals; (b) dispatch Semantics Reviewer and Refusal Boundary Auditor in parallel for every question; (c) for any needs_revision or conflict, recall the relevant specialist with the specific issue and a one-question follow-up scope; (d) run Execution Probe on revised candidates; (e) repeat recall until all verdicts are pass or refuse with evidence; (f) write queries.json only after all questions are resolved. The orchestrator may not delegate final output authority.
